## What is implemented

### Target 1: execution seam (partial)

`AgentToolExecutor` now has package-private injection of lists of `AgentToolExecutionMiddleware` and `AgentToolExecutionObserver`. It creates an `AgentToolExecutionContext`, wraps the existing timeout-backed handler invocation in an `AtomicBoolean` one-shot continuation, executes middleware recursively, and isolates observer runtime exceptions. Public constructors preserve the old behavior by supplying empty lists. The ledger now ignores duplicate success/failure accounting when the invocation is no longer in flight.

This preserves important existing behavior in the exercised path: registry validation, allowed-tool checks, argument validation, duplicate reservation, timeout execution, typed result validation, ledger recording, and existing error codes remain present. The middleware test proves one handler side effect, a second continuation call throws, a throwing observer does not prevent a later observer, and one outcome is observed.

It is nevertheless only a **partial** Target 1 implementation:

1. `DefaultAgentRouter` constructs `AgentToolExecutor` through the public constructor, so production routing always uses empty middleware/observer lists. The seam is test-injectable only from the execution package; there is no production assembly/configuration path.
2. `AgentToolExecutionContext.approvalPresent` is hard-coded `false`, and `deadline` is hard-coded `Instant.MAX`. No middleware actually implements the GAP recommendation that sensitive mutation fail closed when approval context is absent.
3. The middleware/observer interfaces are package-private. That can be intentional for an internal seam, but it prevents an external policy integration and should be an explicit design choice rather than an accidental test-only API.
4. Classification/validation failures returned before `execute(...)` do not pass through middleware or observers. If the intended contract is an observer for every attempted outcome, those paths are currently outside the seam; if only validated execution is intended, this needs explicit documentation/tests.
5. The one-shot guard prevents duplicate continuation calls, but it does not ensure that a middleware returning a successful fabricated result actually invoked the continuation. That may be a valid approval/short-circuit design, but it is not the stronger “exactly one side effect per successful execution” guarantee implied by the GAP wording without a result provenance rule.

### Target 2: provider context projection (partial, useful)

`AgentRequestAssembler` now delegates to `AgentMessageProjector`. The projector copies messages, preserves the first system message and live user tail, groups assistant tool calls with exactly one result per call ID, drops malformed/orphan tool units, removes oldest complete units under the budget, computes UTF-8 serialized-character accounting, estimates tokens as `(chars+3)/4`, and emits `pruned`, `overflow`, removed-unit count, and SHA-256 fingerprint metadata through `AgentContextProjection` and `AgentPreparedRequest`.

`DefaultAgentRouter.replaceSystemMessageForProvider` now replaces the system message on a copy, projects the replacement plus current conversation, and returns a mutable working list so later router appends work. The focused router test confirms the original list is unchanged and the current prompt remains after pruning. This directly addresses the prior immutable-list regression documented in `.saturn_agent_high_roi_qa.md`.

Remaining Target 2 limitations:

1. The metadata is created but not consumed for telemetry, provider request decisions, cache keys, or explicit logging. It is accounting without an observable operational boundary.
2. `estimatedTokens` is a fixed four-characters-per-token heuristic, not provider/tokenizer-aware accounting as the GAP contract requests. The serialized measure includes a custom role/tool representation, not necessarily the actual serialized provider payload.
3. `AgentPreparedRequest` stores projection metadata, but `DefaultAgentRouter` discards it after extracting messages/definitions. There is no end-to-end assertion that metadata corresponds to the exact `LlmRequest` sent on every post-tool turn.
4. `AgentMessageProjector.project` assumes a non-empty source and unconditionally takes the first message. Current callers appear to provide a system message, but the invariant is not defended locally.
5. Malformed tool history sets `overflow=true` and silently drops malformed units. That may be the desired provider-safety behavior, but it needs an explicit policy/test distinguishing intentional sanitization from data loss. The current test only checks an orphan is absent; it does not test assistant/result ordering, duplicate IDs, multiple units, or durable-history hashes.
6. The projector protects the list structure but does not deep-copy individual `LlmMessage` internals. Whether `LlmMessage` is deeply immutable should be confirmed before claiming full copy isolation.
7. The router applies projection after tool results, but subsequent provider responses are not themselves added to the durable history in this method; durable persistence remains delegated elsewhere. The no-mutation claim is supported for the list, not yet by a durable-history before/after test required by the GAP.

### Target 4: resource scheduling and cancellation (partial)

`AgentToolDescriptor` has compatibility constructors defaulting resource sets to empty and validates immutable, nonblank, disjoint read/write sets. `AgentToolExecutionPolicy` classifies tools with writes, non-idempotence, or prerequisites as sequential dependent reads. `AgentToolCallScheduler` keeps contiguous provider order, allows only resource-compatible parallel reads, treats unknown-resource/known-resource mixtures as barriers, and has a package-private `AgentToolBatchContext` with an `Instant` deadline and cancellation token. The scheduler maps timeout/cancellation/interruption to coded results and cancels a timed-out future.

The policy test covers independent reads and a read/write conflict. Existing scheduler tests plus the focused run show no regression in the old ordered/failure behavior.

Remaining Target 4 limitations/correctness risks:

1. `DefaultAgentRouter` calls only the public two-argument `AgentToolExecutor.executeAll`, which always creates an unlimited batch context. The deadline/cancellation path is therefore not reachable from normal production routing.
2. Even in the package-private path, `AgentToolExecutionContext` does not receive the batch deadline/cancellation: executor classification creates contexts with `Instant.MAX`, `approvalPresent=false`, and middleware is not informed that the batch expired/cancelled.
3. `AgentScheduledToolCall.deadline` is populated with `Instant.MAX` and is never consulted by the scheduler. It is dead state rather than per-call deadline propagation.
4. `AgentToolExecutionPolicy.classify(descriptor, previous)` and `isParallelSafe(descriptor, previous)` are added but not used by `AgentToolExecutor`; scheduling independently rechecks resource sets. This duplicates classification logic and creates drift risk. The scheduler does not use the policy’s “unknown is conservative” semantics directly.
5. The scheduler’s `await` computes remaining time separately for each future. If the first future consumes most of the batch deadline, later futures are immediately cancelled/marked, but the code returns one result per call without an explicit batch-level cancellation result policy for already-running sibling calls. This needs adverse tests and a documented expected behavior.
6. A cancelled batch is reported as `TOOL_BATCH_DEADLINE` when cancellation is detected during submission (`executeParallel` always constructs that code/message), even when the token was explicitly cancelled before the deadline. That is a concrete semantic bug in cancellation classification.
7. `AgentToolDescriptor` rejects any overlap between reads and writes. A conventional read-modify-write resource contract can legitimately need the same key in both sets; the GAP recommends optional read/write contracts but does not state that overlap is invalid. This restriction should be justified or relaxed before exposing the API.
8. There are no focused tests for read/read, read/write, write/write, unknown, prerequisite, timeout, cancellation, deadline, start-order, interruption, or real-I/O conflict cases listed in the authoritative GAP test plan. Passing old scheduler tests is insufficient evidence for the new behavior.

## Data-flow review

### Provider request path

`DefaultAgentRouter.route` checks prompt size, serializes by `memoryKey`, loads durable memory and room context, then calls `AgentRequestAssembler.assemble`. The assembler builds system/history/user messages and now projects them before returning `AgentPreparedRequest`. The router copies that projected list, sends it to the client, appends assistant tool calls and tool results, then replaces the system message through a second copy/project cycle before the next provider call. This preserves the session lock and avoids mutating the original assembled/durable list in the tested replacement seam.

The weak point is observability and invariant proof: projection accounting is not carried to the client/telemetry boundary, and the focused tests do not verify exact provider payloads across a full multi-turn tool cycle or durable-history immutability.

### Tool execution path

The router creates a default executor with no middleware/observers, calls public `executeAll`, classifies calls, and passes them to the scheduler. The scheduler uses resource sets directly to form parallel segments. For each scheduled call, the executor validates/reserves and then invokes the middleware chain (empty in production) around the one-shot timeout continuation. Results are ledger-accounted, schema-checked, and returned in provider order.

The weak points are the unconnected batch context, the unused per-call deadline, and the lack of a production middleware construction point. Thus the source contains mechanisms for deadline/cancellation and middleware, but the normal application data flow does not exercise those mechanisms.
