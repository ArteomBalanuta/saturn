# Target 3 — Dynamic Registry Completion Specification

## Scope

Implement only the generation-aware registry improvements authorized by the user and defined in `SATURN_GAP_ANALYSIS.md`. Preserve the existing `AgentTool`, `AgentToolDescriptor`, `AgentToolResult`, and `ToolResponseEnvelope` APIs, startup built-in registration, contextual availability, fail-closed behavior, and `freeze()` compatibility. Do not add RPC, MCP, plugin loading, or broad dynamic extension infrastructure.

## Current baseline

`AgentToolRegistry` currently stores tools in a mutable `LinkedHashMap`, rejects invalid/duplicate names, freezes startup registration, filters `find` and `definitions` by contextual availability, and creates fresh provider JSON definitions. `AgentToolRegistryFactory` registers built-ins and freezes the registry. `SaturnCommandToolCatalog` remains the static built-in source. The baseline registry/tool suite is green.

## Required implementation

### Files

Primary production file:

- `src/main/java/org/saturn/app/agent/tool/execution/AgentToolRegistry.java`

Focused tests:

- `src/test/java/org/saturn/app/agent/tool/execution/AgentToolRegistryTest.java`

Only add a separate small value type if the existing class cannot express an immutable snapshot without compromising compatibility. Do not modify public tool/result contracts or the command catalog unless compilation requires a narrow additive overload.

### Generation

- Add a monotonic `long generation()` accessor.
- Initial generation is `0`.
- Every successful registry mutation increments generation exactly once.
- Failed duplicate, invalid, null, unauthorized, or frozen mutations do not increment generation.
- `freeze()` remains idempotent and does not increment generation.
- Existing startup `register(...).freeze()` behavior remains unchanged.

### Immutable snapshots

- Add an immutable read snapshot API, such as `snapshot()`, containing generation and an immutable ordered tool map.
- A snapshot must remain stable after later registry mutations.
- Existing `find` and `definitions` may delegate through a current snapshot but must preserve their signatures and behavior.
- Snapshot data must not expose mutable internal maps or allow tool replacement through collection mutation.
- Dynamic mutation is explicit and synchronized/thread-safe; concurrent readers observe either the prior or next complete snapshot, never a partially updated map.

### Dynamic mutation

- Preserve `register(AgentTool)` for startup and compatibility.
- Add narrow additive mutation methods only if required by the existing architecture: an explicit refresh/replace operation and deregistration operation may be provided, but must reject mutation while frozen unless an explicit dynamic-mode opt-in exists.
- Default construction remains startup-frozen by the factory; no existing caller silently becomes dynamically mutable.
- Dynamic mutation must validate names and nulls exactly as startup registration does, reject duplicate ownership, and increment generation only after a successful atomic commit.
- Deregistration of a missing name is a no-op or explicit failure, but the choice must be documented and tested; prefer no-op with no generation increment for idempotent lifecycle cleanup.
- No implicit shadowing of built-ins and no unscoped ownership bypass.

### Definition cache

- Cache contextual provider definitions internally by a key containing at least:
  - registry generation;
  - stable caller-context fingerprint;
  - any mode/capability inputs that affect availability or descriptors.
- The cache must never return a definition generated for another context or generation.
- Context fingerprinting must be deterministic and must not include secrets or mutable object identity. Use the actual fields consulted by `AgentTool.isAvailableTo`/`descriptor` where known; if the generic context cannot provide a complete semantic fingerprint, use a conservative no-cache path rather than unsafe reuse.
- Returned `JsonArray` values and nested JSON must remain independent copies, as in current tests.
- Cache failures or descriptor-generation exceptions must fail closed consistently with current behavior; never publish a partially built cache entry.
- Cache invalidation occurs naturally through generation-key changes; explicit clear is optional and must be thread-safe.

## Test-first sequence

1. Add failing tests for initial generation and successful mutation increments.
2. Add failing snapshot isolation/concurrent-read tests.
3. Add failing tests proving failed mutations do not increment generation and frozen registries reject mutation.
4. Add failing cache-isolation tests for two contexts and after mutation/refresh; verify stale definitions are not returned.
5. Add failing duplicate/availability/descriptor mismatch tests through snapshot/cache paths.
6. Implement the smallest compatible slice and rerun the focused registry suite after each vertical behavior.
7. Run the baseline command, full Maven tests, Spotless, package, `git diff --check`, and status hygiene review.

## Security and compatibility gates

- Existing contextual availability remains fail-closed on exceptions.
- Duplicate names remain rejected.
- Built-in catalog registration and startup freeze remain unchanged.
- No public contract removal or signature break for existing callers.
- No provider definition may cross registry generations or caller contexts.
- No untrusted extension execution, plugin discovery, RPC, or MCP lifecycle is introduced.
